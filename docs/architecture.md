# Architecture

rnp-wasm is structured in four layers. Each layer has one responsibility (MECE) and is open for extension via registries (OCP).

```
┌──────────────────────────────────────────────────────────────┐
│  Consumer (Node / Browser / Worker)                          │
├──────────────────────────────────────────────────────────────┤
│  TypeScript wrapper           (ts/)                          │
│   Rnp → Ffi → Keyring → Key                                  │
│   Operations: sign / verify / encrypt / decrypt / generate   │
│   Registries: algorithm, feature, curve   (OCP extension)    │
│   Providers: password / key                (callback surface) │
│   Errors · bytes · handle                  (infra)            │
├──────────────────────────────────────────────────────────────┤
│  Embind boundary   (auto-generated C++ ↔ JS trampolines)     │
├──────────────────────────────────────────────────────────────┤
│  C++ bindings                 (src/cpp/)                     │
│   handle.h   (RAII template)                                  │
│   bindings/{ffi,io,keyring,key,uid,signature,generate,       │
│             sign,verify,encrypt,decrypt,dump}.cpp             │
│   shim_{entropy,clock,fs}.cpp                                 │
│   trampoline.h   (C-callback → JS-callback bridge)            │
├──────────────────────────────────────────────────────────────┤
│  rnp 0.18.1  (third-party/rnp submodule, pinned)             │
│  Botan · zlib · bzip2 · nlohmann/json  (all wasm32)          │
└──────────────────────────────────────────────────────────────┘
```

## Layer responsibilities

### Consumer
Application code. Imports `initRnp` from `rnp-wasm`. Owns the lifecycle of `Ffi`, `Key`, `Input`, `Output` instances via explicit `destroy()` or `using`.

### TypeScript wrapper
Provides the idiomatic API surface. No raw pointers leak. Errors surface as `RnpError` with the rnp result code preserved. All algorithms are validated against the `AlgorithmRegistry` (no stringly-typed switches).

### Embind boundary
Generated by Emscripten from `EMSCRIPTEN_BINDINGS` blocks in `src/cpp/bindings/*.cpp`. Translates C++ class methods into JS class methods, copies bytes between heaps, manages lifetime via reference counting.

### C++ bindings
Thin wrappers around rnp's C API. The `Handle<T, DestroyFn>` template (RAII) ensures all rnp handles are released on scope exit, even on exception. Per-domain files keep each binding in exactly one place (MECE).

### rnp + deps
Source-pinned via Dockerfile + git submodule. We do not modify rnp (no patches in v1). Botan is built minimized to the algorithms rnp uses.

## Why separate repo from rnp

Different release cadence, different toolchain (Emscripten vs. native), different audience (npm consumers vs. system-library consumers). In-tree Emscripten support would pollute rnp's CMake and CI.

## Why Emscripten + Embind (not wasi-sdk or hand-written)

- Embind provides typed C++ class → JS class mapping, automatic lifetime via Embind's reference counting.
- Emscripten provides Asyncify (required for our JS provider callbacks), MEMFS, the JS loader shim.
- wasi-sdk doesn't have Asyncify or a JS-side loader.

## Open/closed principle

New algorithm, curve, hash, or AEAD mode: register in `ts/registry/algorithm.ts`. No code elsewhere changes.

New operation on rnp: add a `bindings/<name>.cpp` with its own `EMSCRIPTEN_BINDINGS` block, plus a `ts/operations/<name>.ts` wrapper. No existing file changes.

## Memory model

JS-side `Uint8Array` is **copied** into the WASM heap on input, and **copied out** on output. This is correct for v1; TODO 38 introduces a pool to eliminate per-call allocations in hot paths.

Provider callbacks (password, key) flow from rnp C → C++ trampoline → Embind JS function → JS callback. Asyncify makes this synchronous from C's perspective.

## Reproducibility

- Docker pins emsdk, Botan, zlib, bzip2 versions.
- CMake builds with `-Oz -flto` and a stable link order.
- CI verifies that two builds of the same commit produce identical `.wasm` bytes.
